# 内容「终身一次下载、永远本地复用」的服务端契约

日期：2026-10-29

客户端从这天起改成：目录每次启动检查更新，新文章照常下载；**正文、音频、词条、封面
一旦下载就永久本地保留，不再重取**（含正文锁定首次下载版本）。

这份文档记录服务端在这个前提下**承诺什么、已经有什么、还缺什么**，避免客户端按
一个并不存在的承诺去做缓存。

## 一、服务端已经成立的保证（核对过代码）

| 保证 | 依据 | 对客户端的意义 |
|---|---|---|
| 已发布文章不会重新生成 | `app/pipeline.py: _upsert_article()` 同 `fingerprint` 直接 `return None` | 同一篇的 `version_id` / `content_hash` 稳定，客户端"锁首版"不会被上游顶掉 |
| 音频只写一次 | `app/pipeline.py` 合成前 `if version.audio is not None: continue`；`scripts/backfill_audio.py` 只处理 `audio is None` | `audio/<article_id>/<level>.mp3` 不会被静默换字节 |
| 音频 URL 永久稳定 | `app/audio_store.py` 头部说明：URL 不含 commit SHA，内容更新靠 `content_hash` 驱动 | 本地缓存的音频不会因为发布新版本而失效 |
| 对象存储带不可变缓存头 | `app/storage.py: R2Storage.put()` → `CacheControl: public, max-age=31536000, immutable` | CDN / 中间层也会长期复用 |
| 没有删除已发布版本的代码路径 | 全仓 `removed` 只出现在统计字典里，无对应实现 | 老详情 URL 不会 404（在保留期内） |

## 二、本次调整

### 1. 索引窗口 3 天 → 14 天（`app/exporter.py`）

原来 `publish_all(topics_days=3)` 写死 3，导致**已经发布的历史日期进不了索引**：
仓库里 `content/data/` 已有 15 天，App 只看得见 3 天，「加载更多」也翻不到更早的。
既然客户端要长期保留旧文章，索引却把可见范围卡在 3 天，方向是相反的。

- `MAX_DAYS_IN_INDEX = 14`，与 `settings.github_keep_days`（仓库保留期 14 天）对齐。
- `export_index()` 增加 clamp：`days` 超过保留期会被截断并告警，避免索引里出现
  一份已经被 prune 掉的日目录（那等于给 App 一个必然 404 的地址）。
- `publish_all(topics_days=None)` 缺省取该常量，`pipeline.py` 两处硬编码的 3 已去掉。

### 2. 词典版本 manifest（`scripts/build_dict.py`）

客户端把分片永久存在本地（`dict-v1/`），而分片路径固定是 `dict/en/<两字母>.json`，
**重建词典等于原地覆盖同一个 key —— 老用户会永远停在旧词条上，且无迹可循**。

- 每次上传后写 `dict/manifest.json`：`version` = 全部分片内容的 sha256 前 16 位。
- 同样的数据重跑 `version` 不变（幂等，不会让所有客户端无谓重下）。
- 位置必须避开 `dict/en/`：`prune_legacy()` 会把该前缀下名字不是恰好两个字母的对象
  当早期"一词一对象"残留删掉。

**客户端契约（待客户端接入）**：启动时比对本地记录的 `version`，一致就继续用本地分片；
不一致才丢弃本地副本重新下载。旧分片对象不删，换版期间老客户端仍能取到可用数据。

### 3. 体积闸门的清理天数跟着保留期走（`app/publish.py`）

`publish_all` 开头有一道体积闸门：仓库超过 jsDelivr 上限的 80% 就先 `prune` 一次。
它原来写死 `keep_days=3`。索引放到 14 天之后这就变成自相矛盾 —— **按 3 天清、按 14 天列**，
等于给 App 发 11 个必然 404 的日期，紧接着的第 ③ 步全量校验会当场判失败（那次发布不生效，
但清理已经发生，日目录已经被删掉了）。

改为 `settings.github_keep_days`，与索引窗口同源。加了一条测试钉住这个参数
（`tests/test_daily_publish.py::test_size_gate_prunes_with_repository_retention`）。

### 4. 其余「写死 3 天」的地方一并收口

同一类问题散在三处，改常量不改它们等于没改：

| 位置 | 原来 | 现在 |
|---|---|---|
| `scripts/republish.py --days` | 缺省 3（这是**修索引的唯一入口**，一跑就把历史又收窄回 3 天，且症状是"索引正常、只是历史变少"，极难发现） | 缺省 `None` → 交给 `publish_all` 取 `MAX_DAYS_IN_INDEX` |
| `app/pipeline.py: _republish_for_alt(days=...)` | 缺省 3 | 缺省 `None` → 同上；两处调用点删掉 `days=3` |
| `app/pipeline.py` 每日发布 | `publish_all(topics_days=3)` | 不再传 |

### 5. 「加载更多」独立出历史清单（`data/archive.json`）

`index.json` 原本同时干两件事：`latest` 是首屏要显示的那一天（内容），`dates` 是
「还能往回翻到哪」（目录）。两者挤在一个数组里，后果是**服务端为了支持分页，必须
把整个保留期都塞进首屏文件**；而调整首屏窗口时，会顺手改变「能翻多远」—— 今天把
3 天改成 14 天就是这么撞上的。

拆开：`index.json` 只管首屏，`data/archive.json`（+ 短路径同名文件）只管翻页。

```json
{ "count": 14, "newest": "2026-10-29", "oldest": "2026-10-16",
  "dates": ["2026-10-29", ...], "retention_days": 14,
  "generated_at": "...", "base_url": "...", "contract": "..." }
```

- **不含任何正文字段**：正文仍是点进去才下载，一次一篇。
- 写清单前会剔除「日目录实际不存在」的日期 —— 列进去就是一个必然 404 的游标。
- 天数同样被 `github_keep_days` 截断；与 `index.json` 在**同一次提交**发出，
  并在更新 `latest` 指针**之前**校验「索引里的每一天都在清单里」（缺一天就拒绝发布，
  因为客户端那里只表现为「没有更早的了」，完全没有报错）。
- `prune()` 显式跳过根目录的 `index.json` / `archive.json` / `latest.json`：它们不是
  「某一天的内容」，不能按日期清。
- 客户端契约：点「加载更多」时才拉，一天最多拉一次、可落盘复用；用 `oldest` /
  `dates` 与本地已有日期求差集，**不要用页码**（日期前移会让同一页码指向不同内容）；
  清单里没有的日期就是确实没有了，不要再回头试。

**为什么是静态文件，不是 `?before=&limit=` 的接口**：内容托管在 GitHub + jsDelivr，
query 不参与路由（客户端自己就在用 `?t=<stamp>` 做 cache busting，正是它不路由的
证据）。要做带参数的接口就得前面挂一个 Worker —— 为一个纯静态清单付运行时成本和
单点故障，不划算。

**客户端切换后可以做的收尾**（尚未做，等客户端接入）：`index.json` 的 `dates`
缩回最近 3 天（首屏就取 3 天），把「翻多远」彻底交给 archive，两者不再互相牵制。
目前保持 14 天是为了兼容还没改的客户端。

## 三、还没解决、需要拍板的

### 1. 内容本身只保留 14 天（硬上限）

`settings.github_keep_days = 14`，`storage.prune()` 会删掉更早的日目录与 `versions/*.json`。
于是：

- **已下载过**的设备：本地永久保留，不受影响（客户端锁定首版正好覆盖这一段）。
- **新装 / 换机**：只能拿到最近 14 天的文章，更早的连详情都下载不到。

要真正做到"任何设备任何时候都能回看"，得把 JSON 也从 GitHub/jsDelivr 迁到对象存储
（jsDelivr 单仓库 50MB 上限，content/ 每天约 110KB，一年约 40MB，顶不住），并同步把
保留期拉长。这是基建 + 成本决定，本次没有动。

### 2. 封面图是第三方热链，不是自有存储

`exporter._image_meta()` 只对白名单图源（unsplash / pexels / wikimedia / openverse）
输出 `type=photo`，URL 直接是对方地址。客户端"封面永久本地"对**已经下载过**的图成立，
但第三方图挂了/换了，新设备就只能看到渐变占位。"封面永远可用"目前不成立；要不要把图
镜像到自有存储，涉及图源许可与署名义务，需要产品确认。

### 3. 没有撤稿 / 更正通道

客户端有 tombstone 与 `RemoteResult.Withdrawn` 的完整处理，但服务端**从不产出**撤回信号
（全仓没有 article 级下架实现）。以前影响有限（下次刷新就会拿到新内容）；现在客户端锁
首版、音频永久本地，一篇有问题内容在已装机设备上就永久存在了。这是本次改动之后
最值得补的能力，但属于新功能，需要产品拍板。
